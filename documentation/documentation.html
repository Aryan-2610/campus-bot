Technical Maintenance Blueprint

Welcome to the core documentation hub for the CampusBot RAG platform. This document acts as a layout map for systems operations, code architecture, and database maintenance tracking.

System Architecture

CampusBot runs a hybrid lexical and semantic Retrieval-Augmented Generation system. Instead of generating text out of thin air, it reads user intent, dynamically queries a specialized internal knowledge matrix, and pipes structured context down to the LLM backend.

Performance Core: Vector lookups use an optimized FAISS database index saved explicitly onto disk space. This completely bypasses processing bottlenecks or repeated data parsing cycles on app startup.

Core Components

The system is modularized cleanly into separated operational modules across the package root:

File Engine Primary Responsibility Dependencies
app.py Flask routing server. Governs endpoints and asynchronously serves web context layers. Flask
engine.py Central execution gateway orchestrating processors, lookups, and context formatting. Internal Modules
retrieval.py Handles dual-track vector space generation, Reciprocal Rank Fusion calculations, and index building. FAISS, pypdf, BM25
query_processor.py Parses text to verify security boundaries (moderation validation) and expands complex queries. langchain_google_genai
prompts.py Centralized ledger managing formatting guidelines and structural JSON return maps. Standard String Forms

Adding New Data/PDFs

When official university notices, examination policies, or structural amendments change, follow this sequence to securely commit information into the engine's long-term memory matrix:

  1. Place your clean, newly gathered .pdf document inside the campus-assistant/data/ folder directory.
  2. To avoid corruption crashes caused by bad parsing structures (such as scraped web login screens named as PDFs), execute your validation cleaner utility: 
    python cleanup_pdfs.py
  3. Because the engine uses persistent caching, you must completely remove old local artifacts so it re-indexes your new files. Clear out the directory storage folder: 
    rm -rf faiss_index/
  4. Re-run the deployment pipeline. The initialization routine will safely step through new text extraction loops, generate token matrices, and rebuild a local production cache automatically.
Attention: If you add over 100 new structural text blocks at once, the system's defensive batch loop will activate to protect your credentials from 429 quota exceptions. Let the runtime process scale down securely without forcing a kill command on the terminal session.

Updating AI Models

If you need to change your underlying models (e.g., swapping to a newer embedding model or upgrading to a different generative LLM), open retrieval.py and engine.py and look for the constructor blocks:

# Changing Embeddings Engine (Inside retrieval.py)
self.embeddings = GoogleGenerativeAIEmbeddings(model="models/your-new-embedding-model")

# Changing Chat Synthesis Model (Inside engine.py & query_processor.py)
self.llm = ChatGoogleGenerativeAI(model="models/your-new-llm-model", temperature=0.1)

Modifying System Instructions & Prompt Rules

The AI's operational rules, behavior guidelines, and JSON structures are decoupled from the code and live entirely inside prompts.py.

If you need to adapt the bot's behavior for a specialized administrative department, open prompts.py and modify the RAG_SYSTEM_PROMPT string. Ensure any custom system prompt additions still instruct the model to return a valid JSON structure matching this required signature:

{
  "answer": "...",
  "inap": false,
  "source_file": "...",
  "confidence": "high"
}

Environment Variables Reference

The system reads operational secrets entirely from an uncommitted .env file root configuration block. Keep this secure:

Variable Key Functional Assignment
GOOGLE_API_KEY Global authorization token used for text embeddings processing and LLM inference generation.
FLASK_ENV Controls environment configurations (Set to production on remote systems).

Handling Rate Limits (429 Resource Exhausted)

If your logs show a 429 RESOURCE_EXHAUSTED error during system builds, it means the API is hitting rate thresholds. The pipeline includes built-in exponential backoff handlers via the @retry framework to gracefully handle this:

@retry(
    wait=wait_exponential(multiplier=2, min=4, max=60), 
    stop=stop_after_attempt(5)
)
def safe_add_chunks(db, chunk_batch):
    db.add_documents(chunk_batch)

If rate limits continue to trigger on large datasets, modify the batch_size variable down to 2 or 3, and increment the delay_seconds parameter inside retrieval.py to extend the API's cooling-off time between requests.
